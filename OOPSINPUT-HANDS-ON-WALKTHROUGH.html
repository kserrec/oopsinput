Your first hour with oopsinput

You have not used this project before. That is the starting point, not a problem. This guide first names every moving piece, then lets you experience the product one safe action at a time. No real project files are used for the dangerous-looking tests.

The one safety rule that matters most oopsinput is an assistance layer, not a safety barrier. When it breaks, times out, or cannot understand a command, it deliberately lets the original command run unchanged. Never test it with a destructive command aimed at your real files, your home directory, the filesystem root, a real remote repository, or a storage device.
What this guide changes The main exercise creates a randomly named directory under /tmp, a tiny Git repository inside it, and oopsinput test records inside it. Terminal-only environment variables keep the exercise away from your normal config and recorded state. The cleanup step removes only that generated directory after validating its name. No command uses sudo, asks for a password, contacts a network service, or edits a dotenv file.

First: what did you build?

Read this before opening a terminal

oopsinput watches the moment when you press Enter in an interactive Zsh terminal. It tries to notice two broad things: a command name that probably contains a typo, and a recognized command shape whose current context makes it unusually consequential. It does not run continuously in the background and it does not replace Zsh.

1. You typeZsh holds the exact text in its editable command buffer.
→
2. The Zsh pluginIntercepts Enter and sends a copy of the buffer plus shell facts to the binary.
→
3. The Rust binaryAnalyzes once, records structural facts, and returns a decision. Then it exits.
→
4. Zsh actsRuns the original, runs an accepted typo correction, restores it for editing, or cancels.

The Zsh plugin

A shell plugin is code loaded into your interactive command shell. This one wraps Zsh’s four “accept this line” actions. Its real source is /home/serrecchia/Projects/oopsinput/zsh/oopsinput.zsh; the installed copy is /home/serrecchia/.local/share/oopsinput/oopsinput.zsh.

The Rust binary

A binary is the compiled executable program. The plugin starts one short-lived oopsinput check process for each submitted command. There is no daemon. Dispatch and the decision flow begin in /home/serrecchia/Projects/oopsinput/src/main.rs.

Evidence and policy

Four layers collect evidence: typo distance; recognized danger shapes; current Git or filesystem context; and an optional local Ollama model. Policy turns that evidence into allow, observe, warn, or confirm. The optional model is disabled by default.

Local structural records

The default log records facts such as decision codes, evidence codes, word counts, outcomes, and timings. It does not record raw command text or paths. The report reads those records locally; nothing is uploaded.

The four visibility modes

ModeWhat you seeWhat still happens
shadowNo prompts at all.Analysis and structural recording continue.
suggestTypo prompts for command names that do not resolve.Danger decisions stay invisible and become hypothetical report data.
warnTypo prompts plus eligible contextual warnings.You can edit, cancel, or run the exact original once.
confirmAlso preserves the strongest confirmation tier.We will not manually test this with a catastrophic command because fail-open makes that unsafe.
Stop point Before continuing, the sentence to hold onto is: “oopsinput advises Zsh at Enter time; Zsh still owns execution, and any internal failure preserves the original command.” If that sentence is unclear, pause here and ask about it before doing the exercises.

Now experience the product

Open one card, complete it, then continue
Use your own Terminal window These are interactive checks: oopsinput reads single keys from the real terminal and inspects the live Zsh widgets in that same shell. They cannot be meaningfully completed by a non-interactive process on your behalf. Keep the same terminal open through Step 19; the isolation variables belong only to that one shell process.
1 Open a brand-new terminal windowThis loads the installed plugin into a fresh interactive Zsh process.

Open your normal Terminal application and create a new window or tab. Do not use an embedded command runner. You should see your ordinary shell prompt.

Expected: a normal prompt where you can type. Nothing from oopsinput needs to appear yet.
2 Ask the installed program to diagnose itselfThis is the live owner check that automation cannot perform for you.

Paste this into that new terminal and press Enter:

"$HOME/.local/bin/oopsinput" doctor
Expected: the output ends with result: ready. It should also say plugin: installed, widgets: 4/4 wrapped in this shell, show a valid config, identify the effective mode, report the model as disabled unless you deliberately configured one, and accept the state permissions.

doctor itself is read-only. Because you submitted the line through the active plugin, the plugin may record one ordinary structural analysis event before the doctor process runs. That distinction is expected.

If it does not end in “ready,” stop here. Do not install, repair permissions, or edit config yet. Reply in chat with: “I stopped at the live doctor check; it did not report ready,” followed by the complete doctor output. Review the output before sharing it, although doctor is designed to escape untrusted text and not print raw command history.
3 Create an isolated practice areaAll later deliberate events and config defaults stay under one generated /tmp directory.

Paste this entire block once:

export OOPSINPUT_HANDSON_DIR="$(mktemp -d /tmp/oopsinput-handson.XXXXXX)"
export OOPSINPUT_STATE_DIR="$OOPSINPUT_HANDSON_DIR/state"
export XDG_CONFIG_HOME="$OOPSINPUT_HANDSON_DIR/config"
export OOPSINPUT_MODE=shadow
print -r -- "Disposable practice area: $OOPSINPUT_HANDSON_DIR"

An environment variable is a named value inherited by programs launched from this terminal. These four values last only in this shell. They do not edit your normal oopsinput config. XDG_CONFIG_HOME points this exercise at an empty config location, so all settings except the explicit mode use safe defaults. OOPSINPUT_STATE_DIR keeps all exercise records separate.

Expected: one printed path beginning with /tmp/oopsinput-handson..
4 Confirm the isolated setupDoctor should now describe the temporary defaults rather than your normal config path. 
"$HOME/.local/bin/oopsinput" doctor
Expected: config says the temporary path is absent and defaults are valid; mode says shadow; widgets remains 4/4; and the result remains ready.
5 Watch an ordinary command pass throughThe common path should feel like oopsinput is not there. 
printf 'ordinary command reached Zsh unchanged\n'
Expected: exactly the sentence ordinary command reached Zsh unchanged, with no oopsinput prompt. The plugin analyzed the line and then gave the exact original buffer back to Zsh.
6 See what Shadow mode meansCreate a safe fake command, mistype it, and observe deliberate silence.

First create a terminal-only alias with a deliberately unusual name:

alias oopspecialx='printf "TYPO CORRECTION WORKED: %s\n"'

Now type the name with one extra q:

oopspecialxq shadow
Expected: no oopsinput prompt. Zsh reports that oopspecialxq was not found. Shadow mode noticed the one-character typo but deliberately stayed invisible and allowed the original typo to fail naturally.

Confirm that hidden observation through the aggregate report:

"$HOME/.local/bin/oopsinput" report
Expected: a nonzero event count and typo.candidate_d1 in the evidence ranking. The report shows structural counts, never the typed alias name.
7 Accept a typo correction in Suggest modeThis is the installed default’s visible daily-use feature.

Change only this terminal’s mode:

export OOPSINPUT_MODE=suggest

Submit the same safe typo with a different argument:

oopspecialxq accepted

Wait until the *** oops? *** block and its two-choice row are visible. run original begins highlighted. Press Tab once to highlight run correction, then press Enter.

Expected: the oopsinput question begins after a clean blank line and displays You typed 'oopspecialxq accepted'. followed by Did you mean 'oopspecialx accepted'?. Tab changes only the highlighted choice on the compact final row. Accepting prints TYPO CORRECTION WORKED: accepted. The argument survives unchanged; only the command name is corrected after your explicit consent. Pressing y would accept immediately as well. If no key is entered for ten seconds, oopsinput instead says it timed out and is running the original unchanged; that message is not acceptance, and the alias must not run.
8 Decline a typo correctionThe original typo must run unchanged, even though it will fail. 
oopspecialxq declined

Wait for the prompt, then press n once.

Expected: the alias does not print anything. Zsh reports oopspecialxq as not found. That error is success for this test: you told oopsinput to preserve and run the original bytes.
9 Cancel a typo completelyNeither the typo nor the correction should run. 
oopspecialxq cancelled

Wait for the prompt, then press Ctrl + C.

Expected: the prompt disappears and a fresh shell prompt returns. You see neither TYPO CORRECTION WORKED nor a “command not found” error, because nothing ran.
If any expected typo prompt is absent The deliberate fail-open outcome is that the original typo runs unchanged and Zsh prints “command not found.” Do not switch to a consequential probe. Stop, keep the terminal output, and report which step lacked the prompt. Prompt tests passed in isolation while this guide was prepared, but a parallel PTY verification run did suppress two prompts under load; the exact cause is not yet proven.
10 Build a disposable dirty Git repositoryThis gives the warning layer real context without risking your work.

Paste this whole block:

mkdir -p "$OOPSINPUT_HANDSON_DIR/dirty-repo"
cd "$OOPSINPUT_HANDSON_DIR/dirty-repo"
git init -q
git symbolic-ref HEAD refs/heads/main
printf 'committed version\n' > tracked.txt
git add tracked.txt
git -c user.name='Oopsinput Walkthrough' -c user.email='walkthrough@example.invalid' commit -q -m 'baseline'
printf 'disposable uncommitted change\n' > tracked.txt
git status --short

A tracked file is a file Git knows about. A commit is the saved baseline. The final printf changes the file after that baseline, creating exactly one disposable piece of uncommitted work.

Expected: git status --short prints M tracked.txt.
11 Cancel a contextual warningSame real Git command, but its only target is the disposable change. 
export OOPSINPUT_MODE=warn

Now submit:

git reset --hard

Wait for the warning, read every line, then press c.

Expected: the warning says the command will discard uncommitted tracked-file changes, reports one modified tracked file, and offers edit, cancel, and run unchanged. After c, nothing runs.

Verify that cancel protected the disposable change:

git status --short
Expected: it still prints M tracked.txt.
If no warning appears, stop. Fail-open may have allowed the reset, which can erase only the disposable change in this fixture. Do not repeat the experiment on real work. Save the complete output and report that Step 11 ran without a warning.
12 Restore the exact command for editingThe warning does not rewrite or execute it. 
git reset --hard

Wait for the warning, then press e. The warning should disappear and the exact text git reset --hard should reappear on your normal editable command line. At that normal prompt, press Ctrl + C to discard the line rather than execute it.

Verify again:

git status --short
Expected: it still prints M tracked.txt.
13 Run the original once, with deliberate consentThis destroys only the known disposable modification. 
git reset --hard

Wait for the warning, then press r.

Expected: Git runs the exact original command and reports that HEAD is at the baseline commit. The disposable uncommitted text is now gone.

Confirm both facts:

git status --short
sed -n '1p' tracked.txt
Expected: the status command prints nothing, and the file prints committed version.
14 See the context-sensitive counterfactualThe identical command should now be silent because there is no work to lose. 
git reset --hard
Expected: Git runs immediately with no oopsinput warning. This is the heart of the product’s danger design: git reset --hard in a dirty repository and the identical text in a clean repository receive different answers because the current consequences differ.
15 Read the local reportTurn the exercise into counts, outcomes, evidence, and latency. 
"$HOME/.local/bin/oopsinput" report
Expected: a nonzero event total; deterministic latency percentiles; ranked decision and evidence codes; and visible warning outcomes containing one each for cancelled, edited, and ran_unchanged. Exact event counts and timings depend on how many verification commands you entered.

A percentile summarizes a distribution. For example, p95 is the measured duration at or below which 95 percent of recorded analyses completed.

16 Prove the default log omitted raw command textUse a fake canary string, never a real secret.

First submit a distinctive, meaningless string as an ordinary command argument:

printf 'OOPSINPUT_PRIVACY_CANARY_4f71\n'

Now search the temporary event log for that exact raw text:

if grep -Fq 'OOPSINPUT_PRIVACY_CANARY_4f71' "$OOPSINPUT_STATE_DIR/events.jsonl"; then
  print -r -- 'FAIL: raw canary text appeared in the event log'
else
  print -r -- 'PASS: raw command text is absent from the event log'
fi
Expected: PASS: raw command text is absent from the event log.

This proves the specific default-log property for the event you just created. It is not a general security proof and it does not mean terminal output is safe to share without reviewing it.

17 Check private state permissionsThe directory should be owner-only; its files should be owner-readable and owner-writable only. 
stat -c 'directory mode: %a' "$OOPSINPUT_STATE_DIR"
find "$OOPSINPUT_STATE_DIR" -maxdepth 1 -type f -printf 'file mode: %m  %f\n' | sort
Expected: the directory mode is 700. Every listed file mode is 600. Those numeric permissions mean only your user account can enter the directory or read and write the files.
18 Purge the isolated recordsThis permanently deletes only oopsinput-owned state under the temporary state path.

The following command invokes purge and checks for the removed directory in the same submitted buffer. That matters: a later separately submitted command would itself be analyzed and would recreate the state directory. 

"$HOME/.local/bin/oopsinput" purge && if [[ ! -e "$OOPSINPUT_STATE_DIR" ]]; then
  print -r -- 'PASS: temporary recorded state was removed'
else
  print -r -- 'FAIL: temporary recorded state still exists'
fi
Expected: purge reports removed state files, followed by PASS: temporary recorded state was removed. The Git fixture and the empty temporary config area remain until the next cleanup step.
19 Remove the disposable practice areaA path-shape guard prevents this cleanup from broadening beyond the directory created in Step 3.

First put the plugin back into silent mode. This line may recreate one temporary state event, which the guarded cleanup immediately removes. 

export OOPSINPUT_MODE=shadow

Then paste this entire block once:

case "$OOPSINPUT_HANDSON_DIR" in
  /tmp/oopsinput-handson.*)
    cd /home/serrecchia/Projects/oopsinput
    rm -rf -- "$OOPSINPUT_HANDSON_DIR"
    unset OOPSINPUT_HANDSON_DIR OOPSINPUT_STATE_DIR XDG_CONFIG_HOME OOPSINPUT_MODE
    unalias oopspecialx 2>/dev/null || true
    print -r -- 'Disposable oopsinput practice area removed'
    ;;
  *)
    print -u2 -- 'REFUSED: the practice-area path did not have the expected safe shape'
    ;;
esac
Expected: Disposable oopsinput practice area removed, followed by your normal prompt. Your current directory is now the real project root; your normal oopsinput config and state resolution are back in effect for later commands.

Test the build like a developer

Automated checks after the human experience

The hands-on section proves that you can feel and understand the product. These checks prove broader mechanical properties. Run them in a normal terminal from the repository. They create compiled files under target/ and temporary test directories; the lifecycle gate uses an isolated fake home and does not edit your real shell setup. Submitting the top-level Cargo and gate commands through your installed plugin can add a few deliberate structural events to your normal state. M8 requires purging all deliberate test data before the later natural-use pilot begins.

Test

Run unit, integration, golden-corpus, lifecycle, and real-terminal behavior checks.

Pass condition: both commands exit successfully with no diff and no warning.

Pass condition: every test group ends with zero failures. The last full M8 acceptance recorded 298 passing tests and one intentionally ignored live-model evaluation harness. Cargo prints separate summaries per test executable, so do not expect one single “298 passed” line.

Know what you have—and have not—proven

A truthful finish line

You have directly exercised

  • live installation diagnosis and all four wrapped Zsh accept widgets;
  • ordinary byte-preserving pass-through;
  • Shadow observation and Suggest-mode typo accept, decline, and cancel;
  • Warn-mode edit, cancel, and run-unchanged outcomes;
  • the same Git command in dirty and clean contexts;
  • aggregate reporting, default raw-text omission, private permissions, and purge;
  • release build and acceptance gates, if you completed the developer section.

You have not proven

  • that every dangerous command shape is recognized;
  • that fail-open behavior can protect against a genuinely destructive test;
  • that Bash, Fish, non-interactive scripts, or agent subprocesses are intercepted;
  • that the optional Ollama layer improves decisions—it is disabled by default;
  • that warning accuracy is ready for a default rollout; that requires a fresh natural-use pilot and review.
Commands that never belong in a manual product test Do not type recursive deletion aimed at / or your home directory, destructive commands in a real repository, force pushes to a real remote, writes to /dev/* devices, filesystem-formatting commands, or privileged removal commands. Automated golden cases test their analysis without executing them.
